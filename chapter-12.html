Chapter 12: Concurrent Programming

Control races, synchronize safely, and design scalable concurrent systems.

Learning Goals

  • Identify data races and protect critical sections.
  • Use mutexes/semaphores/condition variables appropriately.
  • Understand deadlock conditions and prevention patterns.
  • Balance correctness with scalability.

What You Should Internalize

Concurrency increases throughput and responsiveness but introduces nondeterminism. Correct behavior requires explicit coordination when state is shared.

A high-quality concurrent design minimizes shared mutable state and keeps synchronization scope tight and intentional.

Module 1: Shared State and Synchronization

A data race requires concurrent accesses to shared data, at least one write, and missing synchronization that enforces ordering/mutual exclusion.

Mutexes protect critical sections. Semaphores coordinate resource counts and producer-consumer style workflows. Condition variables let threads wait for state transitions without busy waiting.

Module 2: Designing for Correctness and Scale

Correctness comes first: establish invariants and synchronization rules, then measure contention and throughput.

Scalable designs use ownership partitioning, immutable data where possible, and consistent lock ordering to reduce deadlock and bottlenecks.

Module 5: Scenario-Based Practice Sprint

Scenario: A multithreaded service passes unit tests but deadlocks under production traffic. Use the chapter model to narrow causes before editing code.

A practical tactic is to separate mechanism questions from performance questions, then solve each with evidence. This keeps experimentation focused and explainable.

When communicating results, include what changed, what stayed constant, and why the final conclusion is robust against noise.
