What You Should Internalize

Students often learn programming as syntax and forget that every line eventually becomes machine-level actions on physical hardware. This chapter rebuilds that end-to-end view.

The key idea is layered abstraction. Compilers, linkers, loaders, the operating system, and the processor each own a specific part of execution. Performance and correctness issues appear when those boundaries are misunderstood.

Module 1: From Source File to Process

A source file is not directly executable. First, the preprocessor expands directives and macros. Then the compiler translates C into assembly. The assembler creates object files, and the linker combines them with libraries into one executable image.

When you run the executable, the OS loader maps code and data segments into virtual memory, sets up runtime state (stack, argc/argv, environment), and transfers control to program startup code.

This sequence explains many practical errors: undefined reference errors are link-time problems, while segmentation faults are runtime memory-access faults.

Module 2: Why Performance Is a Whole-System Property

Program speed depends on where time is spent: compute, memory stalls, disk I/O, and network latency are all different bottlenecks. A faster CPU cannot eliminate a remote-service round trip.

Memory hierarchy is central. Registers and caches are small and fast; DRAM is larger and slower; storage and network are slower still. Locality-driven code can be dramatically faster with the same algorithmic complexity.

Amdahl-style reasoning helps planning: if a part is serial or I/O-bound, parallelizing the rest gives limited total gain.

Latency mismatch

CPU cycles are tiny; storage/network delays are huge in comparison.

Locality

Data reused soon or near previous addresses is cache-friendly.

Serial fraction

Non-parallelizable work caps total speedup.
